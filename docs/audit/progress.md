## Area notes

**Area 1 (checked and fine):** HMAC exactly per Telegram (`signature` kept in the data-check-string, only `hash` dropped); duplicate keys refused; constant-time comparison over every token; `auth_date` bounded to 12 digits, 24 h old at most, 60 s in the future at most; neither token can be empty; the dev token is accepted only with `NODE_ENV=development` and `ALLOW_DEV_INIT_DATA=true` (the config refuses the flag elsewhere); production refuses placeholder tokens, keys and passwords; the production image and Compose both set `NODE_ENV=production` and the flag to false; the web mock is dev-only and the CI bundle check forbids it; `initData` stays in memory and the Authorization header (redacted from logs); a deleted account is never revived; the Bot API client sends the token only to `api.telegram.org` from an armed production process outside a test run, and otherwise only to a local stand-in; the test setup refuses production settings. Tests cover all of these.

**Area 2 (checked and fine):** every table has row-level security except `schema_migrations` (no runtime grants); the tables' owner is the migration user, never a runtime role; the API login role is NOINHERIT, not superuser, no BYPASSRLS, owns nothing, and the API refuses to start otherwise; no runtime role may create objects in `public`. All 17 SECURITY DEFINER functions pin `search_path` and are not executable by `PUBLIC`; each checks the caller inside (`app_user_id()`). The PRD 3.3 read matrix is one predicate (`can_read_recipe`) shared by the policy and the definer helpers; child tables inherit it; only authors write content; a step links only its own recipe's ingredients and videos; only your own uploads can be attached; share tokens are 128 random bits and open only a published "by link" recipe; reactions cannot use a link's token; timers, cook sessions, saved and reactions are own-rows-only; the snapshot in a timer is computed by the server under the reader's permissions. Membership changes run as `cookbook_system` with role and book checks in code; invite codes are 72 random bits. No user input reaches SQL text (fixed table names and sort expressions; values are bound parameters; search words are quoted lexemes). Tests already cover most of this (`rls`, `recipe-rls`, `books`, `roles`, `saved`, `reactions`, `timers`).

**Area 3 (checked and fine):** the webhook compares the secret header in constant time, refuses without it (401, counted per address with failed sign-ins) and stores nothing; the secret and token never reach a log or the setup command's output; `setWebhook` passes the secret, only `message` and `my_chat_member`, and 10 connections. Each update is recorded in `tg_updates` in the same transaction as its effects, so a repeat delivery is a no-op and a failed one is retried by Telegram. Forwarded text: text only, 4096 characters, known people only, 30 an hour, the parser's pool and time limit, written as the sender under row security, never logged. Timers fire in one statement (`SKIP LOCKED`, a status guard, a database trigger forbidding any other transition, a unique `timer:<id>` dedupe key). The outbox claims with `SKIP LOCKED`; 429 pauses the chat and the bot by `retry_after` without counting an attempt; 403 stops all of that person's messages, sets `bot_started=false` and marks their timers undelivered; 400/404 are final; other errors back off 1 s, 5 s, 30 s, 5 min and fail after 5 attempts. Every piece of user text in a message is cleaned of control and direction characters, cut on grapheme boundaries, HTML-escaped and isolated; templates fill placeholders in one pass; start parameters in links are limited to Telegram's alphabet. Tests: `bot-webhook`, `bot-forward`, `outbox`, `notify-text`, `timer-fire`, `worker-load`.
